# Stage 4. Safe Checkpoint Foundation

`zenthrildb checkpoint data.zdb` фиксирует долговечную границу связанной базы. Результат содержит LSN маркера, LSN синхронизированного префикса WAL и наибольший Transaction ID из префикса. Приложение получает успех только после синхронизации маркера.

## Компоненты и последовательность

```text
DatabaseRuntime (operationsMutex)
  → StorageConsistencyChecker + план RecoveryCoordinator в режиме проверки
  → sync WAL → PageManager::flushDirtyPages → append SafeCheckpoint → sync WAL
```

Runtime держит тот же мьютекс, что и CRUD и DDL. Другие штатные операции записи ждут завершения checkpoint. Межпроцессная блокировка действует весь срок жизни FileManager для данного пути. Самостоятельный BufferManager не входит в рабочий runtime и его незащищённые записи не входят в гарантию. PageManager синхронизирует общий файл страниц, заголовка, каталога и free-list. Dirty-флаги очищаются после успешного барьера.

| Состояние | Операция и переход |
|---|---|
| IDLE → PREPARING | Проверка привязки, согласованности, отсутствия активной транзакции и совпадения файла с итоговым планом REDO/UNDO. Старые незавершённые транзакции допустимы, если их эффекты уже сняты. |
| WAL_DURABLE | Успешная системная синхронизация WAL. Граница равна LSN последнего полного кадра, 0 для пустого потока. |
| PAGES_FLUSHING → PAGES_DURABLE | Синхронизация файла базы. Она включает метаданные и file length. До её завершения новый кадр отсутствует. |
| CHECKPOINT_PUBLISHING | Добавление одного полного кадра с CRC в существующий WAL. Замен файлов и файловых каталогов на этом шаге нет. |
| CHECKPOINT_DURABLE → COMPLETED | Системная синхронизация WAL завершилась, возвращается результат. |
| FAILED | Ошибка передаётся вызывающему. Runtime помечает дескриптор непригодным для дальнейшей записи. Новый экземпляр выполняет обычное восстановление и может повторить операцию. |

Порядок мутации остаётся `sync WAL image → запись страницы → sync базы → sync COMMIT`. Checkpoint подтверждает уже восстановленное состояние, проверяемое по полным образам. Максимальный LSN сам по себе не заменяет системную синхронизацию.

## Формат и открытие

Кадр WAL типа 14 имеет обычный заголовок с LSN и CRC и фиксированный payload 52 байта. Little-endian: версия u32 (1), UUID (16 байт), поколение (16 байт), durable WAL LSN u64, верхняя граница Transaction ID u64. Идентификатор checkpoint равен LSN кадра. CRC охватывает и payload. Тип 7 остаётся пустым информационным маркером.

При открытии до изменений проверяются CRC, версия, размер, UUID, LSN предыдущего кадра и верхняя граница Transaction ID. После `snapshotLsn` проверяется текущее поколение. Унаследованные маркеры до или на этой границе сохраняют поколение источника и имеют историческое значение. Старые Stage 2/3 читатели связанного WAL отклоняют тип 14. Legacy базы продолжают открываться, для checkpoint требуется явный снимок.

Recovery анализирует все кадры, включая образы до checkpoint. При неполном последнем кадре существующая процедура может убрать только незавершённые байты после проверки плана. Полные кадры сохраняются. Если процесс завершился до синхронизации маркера, на диске может оказаться отсутствующий, неполный или полный кадр. Полный корректный кадр безопасно принять и синхронизировать при открытии, поскольку обе предыдущие синхронизации уже прошли. Если вызов вернул ошибку, успешного ответа не было независимо от обнаруженного позже кадра.

Полный кадр с ошибкой CRC или несогласованными полями приводит к отказу открытия до изменения файлов. Предыдущий маркер и весь пригодный префикс остаются на диске. Для диагностики или восстановления используется проверенная копия.

## Платформы и пределы

На Linux синхронизация использует `fsync`, на Windows — `FlushFileBuffers`. В существующей паре checkpoint не создаёт имён и не делает rename, поэтому отдельный барьер родительского каталога ему не нужен. Создание базы и публикация снимка имеют собственные процедуры. Гарантии зависят от честного подтверждения записи ОС, файловой системой и устройством. Контейнерный Linux и тесты прерывания процесса не моделируют отключение питания, потерю контроллера и все сетевые ФС. [Linux fsync](https://man7.org/linux/man-pages/man2/fsync.2.html), [Windows FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers)

## Приёмка

Регрессии `ctest -L checkpoint` покрывают повторный checkpoint, конкурентные операции, сохранение побайтного префикса, совместимость снимков, ремонт из старых образов, повторное открытие и Debug-инъекции I/O. Дочерние процессы проходят точки до вызова, подготовки, после durable WAL и страницы, на частичном кадре, после записи до sync, после sync и после возврата. В checkpoint нет записи dirty pages из буфера, отдельного файла метаданных, rename и синхронизации каталога. Соответствующие ошибки проверяются в существующих тестах мутаций либо неприменимы к выбранной схеме.

Существующие наборы `ZenthrilDBTests` и `ZenthrilDBSecurity` подтверждают совместную работу с предшествующими этапами. Для полного прогона используется `ctest --test-dir BUILD -C CONFIG --output-on-failure --no-tests=error --timeout 300`. Набор `ZenthrilDBCheckpoint` добавлен к полному прогону. Штатный Release собирается без инъекций.

| Платформа | Debug | Release |
|---|---|---|
| Windows x64, MSVC | CTest 3/3, 129,06 с. Установленный CLI пройден. | CTest 3/3, 62,27 с. Установленный CLI пройден. |
| Ubuntu 24.04.5, GCC 13, Docker | CTest 3/3, 126,46 с. Установленный CLI пройден. | CTest 3/3, 34,51 с. Установленный CLI пройден. |

Во всех конфигурациях CLI добавил checkpoint и прочитал подтверждённую запись после повторного открытия. Предыдущий WAL сохранился как побайтно идентичный префикс. Регрессии подтверждают ремонт из полных образов до checkpoint, отказ без изменений при ошибочных метаданных и правильную границу после UNDO.

Окно ремонта, счётчики и WAL остаются полными. Сокращение журнала, криптографическая аутентификация и защита от отката согласованной пары требуют отдельных решений. [Дорожная карта](roadmap/STORAGE_RECOVERY_NEXT_RU.md)
