## Назначение прогона

WAL и commit, физическое восстановление REDO/UNDO, повторное открытие, snapshot и checkpoint, ошибки записи и синхронизации, файловые пути, лимиты и конкурентный доступ. Все новые данные созданы во временных каталогах. Рабочая mydb.zdb пользователя в AppData\Local\ZenthrilDB\data не открывалась.

Shannon предназначен для веб-приложений и API. По уточнению владельца проверяется локальная СУБД через существующие тесты и CLI. Новый запуск Shannon в рамках этого прогона не выполнялся.

## Сборка и тесты

Отдельный каталог Windows x64 с Visual Studio 18 2026. CMake и CTest берутся из C:\Users\User\AppData\Roaming\Python\Python313\site-packages\cmake\data\bin.

~~~powershell
cmake -S . -B build-21-win/db-verification-20261120 -G "Visual Studio 18 2026" -A x64
cmake --build build-21-win/db-verification-20261120 --config Debug --parallel 3
ctest --test-dir build-21-win/db-verification-20261120 -C Debug --output-on-failure --no-tests=error --timeout 240
cmake --build build-21-win/db-verification-20261120 --config Release --parallel 3
ctest --test-dir build-21-win/db-verification-20261120 -C Release --output-on-failure --no-tests=error --timeout 240
~~~

Debug прошёл все 5 групп за 205,14 с. Основные тесты 105,65 с, Security 15,65 с, Checkpoint 42,29 с, Snapshot 29,03 с, Hardening 12,47 с. Детальный журнал Debug сохранён отдельно, строк SKIP в нём не найдено. Release прошёл все 5 групп за 106,42 с. Основные тесты 57,22 с, Security 8,38 с, Checkpoint 19,57 с, Snapshot 10,37 с, Hardening 10,83 с. Обе конфигурации собраны успешно в новом каталоге. Неудачных тестов в этих прогонах нет. В Debug CMake определяет ZENTHRILDB_ENABLE_FAULT_INJECTION для ядра и тестов. В Release инъекции отключены. Поэтому отдельное прохождение Debug обязательно для выводов об инъекциях и дополнительных аварийных сценариях.

## Дополнительный тест повреждений через CLI

Скрипт build-21-win/db-verification-20261120/corruption_check.py создаёт собственную базу, подтверждённую строку и checkpoint. После snapshot он создаёт 44 отдельные копии и меняет байты или длины файлов. Для каждой копии требуется ошибка verify-snapshot и совпадение SHA-256 всех четырёх файлов до и после проверки.

Проверяются 13 смещений манифеста, 6 смещений baseline, 7 смещений WAL, 6 смещений рабочего файла, а также три варианта усечения каждого из четырёх файлов. Это детерминированные негативные сценарии. Полноценный coverage-guided fuzzing этим набором не выполняется.

Также скрипт проверяет побайтовое совпадение backup с опубликованным четырёхфайловым комплектом и читает подтверждённое значение. SHA-256 исходных файлов базы и WAL должен сохраниться.

Первый запуск выполнен на CLI Windows Release, собранном 19 ноября из того же рабочего кода. Все 44 копии отклонены без изменения входных файлов, backup и исходные SHA-256 совпали. JSON первого запуска сохранён в build-21-win/db-verification-20261120/corruption-result.json. Новые Debug и Release CLI повторно прошли по 44 сценария, проверку backup и исходных SHA-256. Результаты сохранены в corruption-Debug-result.json и corruption-Release-result.json.

## Ограничения

Новый Linux-прогон недоступен. Docker Desktop Linux engine не отвечает по named pipe. Результаты прошлых Linux-прогонов не учитываются как проверка текущего запуска.

Модель тестов включает системные вызовы синхронизации, исключения I/O и аварийный выход процесса. Она не доказывает поведение накопителя при отключении питания, неисправном контроллере или ошибках write cache.

Остаются границы ранее задокументированной архитектуры. Path-based операции требуют доверенного каталога. При отсутствии обоих sidecar-файлов действует совместимый путь полного WAL replay. Полный WAL сохраняется. SQL, B+Tree, MVCC и защита от согласованного злонамеренного отката требуют отдельных этапов.
