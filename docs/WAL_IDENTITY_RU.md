# WAL Identity и поколения снимков

## Карта операций

| Операция | Реализация и точка проверки |
|---|---|
| Создание | `DatabaseRuntime` запрашивает связанную пару у `FileManager`. Идентичность записывается в страницу 0 и в начало WAL. WAL и .zdb синхронизируются. |
| Открытие | `FileManager::openDatabase` удерживает блокировку и проверяет заголовок и страницу 0. `LogManager` открывает существующий WAL и проверяет идентичность перед чтением кадров. |
| Чтение, append и повторный запуск | `WriteAheadLog` оставляет префикс вне потока записей. `LogManager` восстанавливает следующий LSN по журналу. Незавершённый хвост блокирует append до восстановления. |
| Recovery | `RecoveryCoordinator` проверяет границу снимка, Page LSN и план транзакций до исправления хвоста. Затем выполняет физический REDO/UNDO. |
| Checkpoint и обрезка | Тип 7 остаётся пустым маркером. Runtime публикует [проверяемый SafeCheckpoint](SAFE_CHECKPOINT_RU.md) типа 14. Сокращение истории связанного WAL запрещено. Исправление неполного хвоста сохраняет префикс. |
| Backup | `backup` сохраняет точную пару файлов, включая поколение. |
| Снимок и миграция | `snapshot` восстанавливает и проверяет рабочую копию. Публикует отдельный каталог, сохраняя исходные UUID, кадры WAL и LSN. |

## Формат и идентификация

Префикс .zdb по-прежнему занимает 48 байт. Для привязанных баз страница 0 имеет тип Metadata, формат страницы v2, Page LSN 0 и payload длиной 60 байт. Старый режим обозначен пустой нулевой страницей 0 формата v1. В связанной базе страница 0 неизменяема для обычной записи. Исторические образы заголовка затрагивают только 48-байтовый префикс.

Первые 60 байт связанного WAL совпадают с payload страницы 0. Поля little-endian.

| Смещение | Поле |
|---:|---|
| 0 | Magic `ZDBI` |
| 4 | uint32 версия, сейчас 1 |
| 8 | uint32 размер, сейчас 60 |
| 12 | 16 байт поколения |
| 28 | uint32 резерв, 0 |
| 32 | 16 байт UUID базы |
| 48 | uint64 граница снимка |
| 56 | CRC32 первых 56 байт |

Нулевые UUID и поколение в связанной паре запрещены. Токен поколения получается из системного RNG Windows/Linux, а не из счётчика, поэтому переполнения поколения нет. Границу задаёт LSN последнего полного кадра на момент снимка. Значение 0 обозначает начало новой истории. Максимальный uint64 зарезервирован и отклоняется. При открытии ненулевая граница должна присутствовать среди полных записей. Page LSN ни одной существующей страницы не должен превышать последний LSN WAL.

Префикс WAL защищает все типы кадров одинаково. Полные заголовки проверяются до чтения payload. Неверная версия, тип, размер, порядок LSN или формат checkpoint связанного WAL приводят к отказу. Системные и транзакционные записи не содержат копии UUID. Типизированная запись MetadataUpdated проверяется при startup recovery как информационная, физические изменения берутся из образов страниц.

## Открытие и отказ

1. Получить блокировку и проверить существование обычных файлов. Открытие пары не создаёт новый WAL при отсутствии исходного.
2. Проверить формат и CRC заголовка, CRC страницы 0 и соответствие её UUID базе.
3. Прочитать префикс WAL, проверить формат, длину, CRC, UUID, поколение и границу. Форматы обеих сторон должны согласовываться.
4. Проверить кадры, строгий порядок LSN, наличие границы и допустимость recovery. Проверить UUID в обоих образах каждого исторического заголовка. Незавершённый хвост на этом этапе только отмечается.
5. Только после успешной проверки исправить неполный хвост, выполнить REDO/UNDO и синхронизировать файлы.

При отказе идентификации содержимое .zdb и .wal не меняется. Файл блокировки может появиться как часть открытия. Старый WAL без образов заголовка открывается в режиме совместимости со старыми гарантиями. Явная миграция создаёт связанную пару. Предыдущий читатель не поддерживает новый заголовок WAL. Нулевое поле на смещении 28 даёт ему распознать несовместимость полного префикса без обработки его как неполного кадра.

## Создание нового поколения и откат

Выполнить `zenthrildb snapshot source.zdb NEW_DIRECTORY` при остановленном приложении. Родитель нового каталога должен существовать и быть доступен только доверенным операторам. Команда под блокировкой копирует исходную пару в отдельный временный каталог рядом с назначением, выполняет recovery на копии, присваивает новое поколение, повторно проверяет пару и синхронизирует оба файла. Один rename публикует каталог целиком, с отказом при существующем назначении. Откат использует исходную пару. После аварии до публикации может остаться временный каталог `.snapshot-<token>`. Для повтора используйте отдельное назначение и проверьте опубликованный снимок перед переключением приложения.

## Границы гарантий

- Идентичность и CRC обнаруживают несовместимые пары и случайное повреждение. Криптографическое подтверждение автора и внешняя защита от отката запланированы отдельно.
- Прежний WAL другого поколения и WAL без обязательной записи границы отвергаются. Полностью согласованная старая пара и более короткий WAL того же поколения, сохранивший границу и все требуемые Page LSN, могут быть допустимы. Для обнаружения такого отката нужен доверенный внешний минимум LSN или якорь снимка.
- Снимок сохраняет весь доступный WAL. Граница снимка сама по себе не разрешает сокращать журнал. Долговечность физического носителя, исчерпание места при копировании и более широкая защита путей остаются отдельными проверками.

Регрессии запускаются через `ctest -L security`. Они используют временные базы и проверяют несовместимые пары, повреждённые идентификаторы и заголовки, LSN, checkpoint, legacy-миграцию, повторное открытие, аварийный выход до публикации в Debug и побайтовую неизменность при отказе. Следующие этапы описаны в [плане восстановления и checkpoint](roadmap/STORAGE_RECOVERY_NEXT_RU.md).
