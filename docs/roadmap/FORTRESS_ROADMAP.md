# Дорожная карта ZenthrilDB и Fortress‑20

Основная последовательность сохранена. Меры безопасного хранения и Security Foundation идут параллельно со Storage Reliability и подготовкой API. Таблица задаёт переходы и проверяемые результаты. [Критерии локального v1.0](../RELEASE_ACCEPTANCE_RU.md) и [общая архитектура](../architecture/DATABASE_ARCHITECTURE.md).

| Этап | Зависимости | Результат приёмки |
|---|---|---|
| 1. Storage Reliability | Текущие форматы страниц, заголовка и WAL | Проверенная привязка журнала, WAL-before-data, durable COMMIT, crash/reopen, torn writes, checkpoint и лимиты. Метаданные и free-list согласованы после отказа. |
| 2. Record Manager | Стабильная мутация страниц и владение | CRUD, многостраничные значения, атомарные ссылки и освобождение, reopen и проверка старых записей. |
| 3. B+Tree | Страницы, allocator, heap и координация WAL | Split/merge, удаление, порядок ключей, согласованность heap/index и аварийное восстановление. |
| 4. Transaction Manager и MVCC | Heap, B+Tree, WAL и идентичность транзакций | Публичные многооперационные транзакции, snapshot visibility, commit/rollback, повтор recovery и сборка версий. |
| 5. Lock Manager Integration | Границы транзакций и политика видимости | Дедлок, отмена, таймаут, освобождение при ошибке и проверка на нескольких потоках. |
| 6. Query/API | Семантика транзакций, индекс, лимиты | Базовый SQL DDL/DML или отдельно утверждённый KV контракт, валидация входа, ограничение памяти и времени. |
| 7. Backup/Restore | Снимок транзакций, поколения WAL и политика формата | Восстановление пары на новой площадке, проверка данных и целостности, проверяемое обновление и откат. |
| 8. Security Foundation | Политики и границы runtime, часть работ параллельна этапу 1 | Безопасные пути и конфигурация, минимизация событий, отказ по умолчанию, квоты, негативные тесты и fuzzing. |
| 9. Cryptographic Engine | Проверяемый WAL/recovery, безопасный dirty flush, утверждённый формат и ключевой провайдер | Изолированное управление ключами для v1.0. Шифрование как отдельный проверяемый результат после утверждения формата: AEAD, версионирование, ротация, повторное открытие и восстановление. |
| 10. Fortress Sentinel | Схема аудита, проверяемая политика, идентичность агента | Независимые наблюдатели, подписанные события, ограниченные действия, обратимость и тест отказа агента. |
| 11. Server Protocol | Query/API, MVCC, идентичность, TLS, квоты и готовность Sentinel | Версионированный протокол и Go-драйвер, отмена и дедлайны, проверка полномочий и перегрузки. |
| 12. Полная проверка Fortress‑20 | Реализованные уровни, готовые эксплуатационные процедуры | Чистая матрица Windows/Ubuntu, нагрузка, испытания сбоев, независимый review и практическое восстановление. |

Привязка UUID, поколения и границы LSN описана в [WAL Identity](../WAL_IDENTITY_RU.md). [Физическое восстановление](../PHYSICAL_RECOVERY_RU.md) использует полные образы связанных пар. [Safe checkpoint](../SAFE_CHECKPOINT_RU.md) подтверждает границу и сохраняет историю WAL. Дальнейшая задача этапа 1 — доказать возможность ремонта из проверенного базового снимка перед сокращением истории. Параллельная задача этапа 8 — операции с файлами через проверенные дескрипторы.
