# Резервное копирование и восстановление ZenthrilDB

Для локальной базы `data.zdb` журнал хранится рядом в `data.wal`. Резервная копия содержит оба файла из одной остановленной базы. Для снимка Stage 5 копируйте также `data.zdb.baseline` и `data.zdb.snapshot` из того же комплекта. Файл `data.zdb.lock` нужен для блокировки при открытии и создаётся автоматически. Его можно исключить из копии. При обслуживании рабочей базы сохраняйте её файл блокировки на месте.

## Резервная копия через CLI

Закройте процессы, использующие базу, чтобы CLI мог получить эксклюзивную блокировку. Выполните `zenthrildb backup data.zdb backup-001`. Каталог `backup-001` создаёт команда, его родительский каталог должен существовать. Команда проверяет согласованность, синхронизирует файлы и сохраняет пару базы и WAL. Сохраните контрольные суммы и проверьте копию по инструкции ниже.

## Снимок нового поколения

Для отдельной копии, которая будет использоваться на запись, остановите процессы исходной базы и выполните `zenthrildb snapshot data.zdb snapshot-001`. Укажите новый каталог внутри существующего каталога с доверенными правами доступа. Команда берёт эксклюзивную блокировку исходной базы, копирует файлы и выполняет восстановление и смену поколения на копии. Исходные `.zdb` и `.wal` сохраняют свои байты.

Для перехода со старого поддерживаемого формата используйте ту же команду. Она создаёт комплект нового поколения. Выполните `zenthrildb verify-snapshot snapshot-001/data.zdb` и проверьте ожидаемые прикладные данные, прежде чем направлять приложение на снимок. `zenthrildb verify-baseline snapshot-001/data.zdb` проверяет собственно базовое состояние с манифестом. Сохраняйте исходный комплект для возврата к состоянию на момент копирования. Подтверждённые в новой копии операции при таком возврате переносятся отдельно. [Спецификация снимков](SNAPSHOT_FOUNDATION_RU.md).

Команда `backup` сохраняет идентичность и поколение исходной пары. Команда `snapshot` сохраняет UUID базы и присваивает новый идентификатор поколения. При открытии журнал должен совпадать с базой по UUID и поколению и содержать записи как минимум до LSN создания снимка. В новом каталоге может присутствовать штатный файл блокировки. Проверка происхождения файлов и обнаружение отката всей согласованной пары требуют отдельной доверенной контрольной информации.

## Ручная резервная копия

1. Остановите все процессы, открывающие базу, и исключите автоматический перезапуск на время копирования. Если остановка произошла из-за ошибки записи, сохраните исходную пару отдельно перед любыми попытками восстановления.
2. Скопируйте весь комплект в новый каталог. Для снимка Stage 5 включите оба дополнительных файла. При сбое копирования начните заново с новым каталогом.
3. Запишите SHA-256 каждого файла, дату и версию программы, которой база открывалась. Проверьте копию, восстановив её в отдельный каталог по инструкции ниже.

Пример для PowerShell. Выполняйте из каталога остановленной базы.

```powershell
New-Item -ItemType Directory -Path 'backup-001' -ErrorAction Stop | Out-Null
$artifacts = 'data.zdb','data.wal','data.zdb.baseline','data.zdb.snapshot'
Copy-Item -LiteralPath $artifacts -Destination 'backup-001' -ErrorAction Stop
$copies = $artifacts | ForEach-Object { Join-Path 'backup-001' $_ }
Get-FileHash -Algorithm SHA256 -LiteralPath $copies |
  ForEach-Object { '{0}  {1}' -f $_.Hash.ToLowerInvariant(), (Split-Path -Leaf $_.Path) } |
  Set-Content -LiteralPath 'backup-001/SHA256SUMS' -Encoding ascii -ErrorAction Stop
```

Пример для Linux.

```sh
mkdir backup-001 &&
cp -- data.zdb data.wal data.zdb.baseline data.zdb.snapshot backup-001/ &&
(cd backup-001 && sha256sum data.zdb data.wal data.zdb.baseline data.zdb.snapshot > SHA256SUMS)
```

## Восстановление и проверка

Оба примера рассчитаны на комплект Stage 5. Для обычной базы достаточно `data.zdb` и `data.wal`.

1. Сверьте SHA-256 каждого файла с контрольными суммами, сохранёнными при резервном копировании.
2. Скопируйте комплект в новый пустой каталог. Снова сверьте SHA-256 до первого открытия. Для снимка выполните `zenthrildb verify-snapshot restore-001/data.zdb`. Сохраните исходную резервную копию для повторной проверки.
3. Откройте восстановленную пару той же версией ZenthrilDB, которой база открывалась ранее. Если установлен CLI, используйте `zenthrildb check restore-001/data.zdb`. Открытие выполняет восстановление по WAL и может изменить оба файла, поэтому проверяйте рабочую копию.
4. Проверьте наличие ожидаемых таблиц и записей прикладным чтением. Успешная проверка структуры подтверждает согласованность доступных данных. Она не определяет, все ли ожидаемые записи входят в резервную копию.
5. Для ввода восстановленной базы в работу направьте приложение на проверенную пару в новом каталоге. Прежнюю пару сохраните до завершения прикладной проверки.

## Ошибки при открытии

| Сообщение или признак | Действие |
|---|---|
| База уже открыта | Закройте другой процесс. Наличие файла блокировки само по себе не означает, что блокировка удерживается. |
| WAL отсутствует | Найдите соответствующий журнал из той же резервной копии или восстановите другую полную пару. |
| Несовпадение UUID, поколения или LSN снимка в WAL | Открытие остановлено до восстановления. Сохраните оба файла, найдите согласованную пару из одного снимка и сверьте её контрольные суммы. |
| Ошибка CRC, формата или Page LSN | Сохраните исходные файлы и сообщение об ошибке. Для восстановления используйте проверенную резервную копию. |
| Ошибка записи или системной синхронизации | Сохраните файлы и диагностическое сообщение. Проверьте доступное место и состояние носителя перед повторным открытием копии. Если ошибка произошла во время commit, проверьте состояние соответствующей записи после восстановления перед повтором операции. |

Проверяйте совместимость новой версии на отдельной копии базы. Для возврата к предыдущей версии используйте пару, сохранённую до первого открытия новой версией.
