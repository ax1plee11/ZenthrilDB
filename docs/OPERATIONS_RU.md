# Резервное копирование и восстановление ZenthrilDB

Для локальной базы `data.zdb` журнал хранится рядом в `data.wal`. Резервная копия содержит оба файла из одной остановленной базы. Для снимка Stage 5 копируйте также `data.zdb.baseline` и `data.zdb.snapshot` из того же комплекта. Файл `data.zdb.lock` нужен для блокировки при открытии и создаётся автоматически. Его можно исключить из копии. При обслуживании рабочей базы сохраняйте её файл блокировки на месте.

## Резервная копия через CLI

Закройте процессы, использующие базу, чтобы CLI мог получить эксклюзивную блокировку. Выполните `zenthrildb backup data.zdb backup-001`. Каталог `backup-001` создаёт команда, его родительский каталог должен существовать. Команда проверяет согласованность, синхронизирует файлы и сохраняет пару базы и WAL. Сохраните контрольные суммы и проверьте копию по инструкции ниже.

## Снимок нового поколения

Для отдельной копии, которая будет использоваться на запись, остановите процессы исходной базы и выполните `zenthrildb snapshot data.zdb snapshot-001`. Укажите новый каталог внутри существующего каталога с доверенными правами доступа. Команда берёт эксклюзивную блокировку исходной базы, копирует файлы и выполняет восстановление и смену поколения на копии. Исходные `.zdb` и `.wal` сохраняют свои байты.

Для перехода со старого поддерживаемого формата используйте ту же команду. Она создаёт комплект нового поколения. Выполните `zenthrildb verify-snapshot snapshot-001/data.zdb` и проверьте ожидаемые прикладные данные, прежде чем направлять приложение на снимок. `zenthrildb verify-baseline snapshot-001/data.zdb` проверяет собственно базовое состояние с манифестом. Сохраняйте исходный комплект для возврата к состоянию на момент копирования. Подтверждённые в новой копии операции при таком возврате переносятся отдельно. [Спецификация снимков](SNAPSHOT_FOUNDATION_RU.md).

Команда `backup` сохраняет идентичность и поколение исходной пары. Команда `snapshot` сохраняет UUID базы и присваивает новый идентификатор поколения. При открытии журнал должен совпадать с базой по UUID и поколению и содержать записи как минимум до LSN создания снимка. В новом каталоге может присутствовать штатный файл блокировки. Проверка происхождения файлов и обнаружение отката всей согласованной пары требуют отдельной доверенной контрольной информации.

## Ручная резервная копия

1. Остановите все процессы, открывающие базу, и исключите автоматический перезапуск на время копирования. Если остановка произошла из-за ошибки записи, сохраните исходную пару отдельно перед любыми попытками восстановления.
2. Скопируйте весь комплект в новый каталог. Для снимка Stage 5 включите оба дополнительных файла. При сбое копирования начните заново с новым каталогом.
3. Запишите SHA-256 каждого файла, дату и версию программы, которой база открывалась. Проверьте копию, восстановив её в отдельный каталог по инструкции ниже.

Пример для PowerShell. Выполняйте из каталога остановленной базы.

```powershell
New-Item -ItemType Directory -Path 'backup-001' -ErrorAction Stop | Out-Null
$artifacts = 'data.zdb','data.wal','data.zdb.baseline','data.zdb.snapshot'
Copy-Item -LiteralPath $artifacts -Destination 'backup-001' -ErrorAction Stop
$copies = $artifacts | ForEach-Object { Join-Path 'backup-001' $_ }
Get-FileHash -Algorithm SHA256 -LiteralPath $copies |
  ForEach-Object { '{0}  {1}' -f $_.Hash.ToLowerInvariant(), (Split-Path -Leaf $_.Path) } |
  Set-Content -LiteralPath 'backup-001/SHA256SUMS' -Encoding ascii -ErrorAction Stop
```

Пример для Linux.

```sh
mkdir backup-001 &&
cp -- data.zdb data.wal data.zdb.baseline data.zdb.snapshot backup-001/ &&
(cd backup-001 && sha256sum data.zdb data.wal data.zdb.baseline data.zdb.snapshot > SHA256SUMS)
```

## Восстановление и проверка

Оба примера рассчитаны на комплект Stage 5. Для обычной базы достаточно `data.zdb` и `data.wal`.

1. Сверьте SHA-256 каждого файла с контрольными суммами, сохранёнными при резервном копировании.
2. Скопируйте комплект в новый пустой каталог. Снова сверьте SHA-256 до первого открытия. Для снимка выполните `zenthrildb verify-snapshot restore-001/data.zdb`. Сохраните исходную резервную копию для повторной проверки.
3. Откройте восстановленную пару той же версией ZenthrilDB, которой база открывалась ранее. Если установлен CLI, используйте `zenthrildb check restore-001/data.zdb`. Открытие выполняет восстановление по WAL и может изменить оба файла, поэтому проверяйте рабочую копию.
4. Проверьте наличие ожидаемых таблиц и записей прикладным чтением. Успешная проверка структуры подтверждает согласованность доступных данных. Она не определяет, все ли ожидаемые записи входят в резервную копию.
5. Для ввода восстановленной базы в работу направьте приложение на проверенную пару в новом каталоге. Прежнюю пару сохраните до завершения прикладной проверки.

## Ошибки при открытии

| Сообщение или признак | Действие |
|---|---|
| База уже открыта | Закройте другой процесс. Наличие файла блокировки само по себе не означает, что блокировка удерживается. |
| WAL отсутствует | Найдите соответствующий журнал из той же резервной копии или восстановите другую полную пару. |
| Несовпадение UUID, поколения или LSN снимка в WAL | Открытие остановлено до восстановления. Сохраните оба файла, найдите согласованную пару из одного снимка и сверьте её контрольные суммы. |
| Ошибка CRC, формата или Page LSN | Сохраните исходные файлы и сообщение об ошибке. Для восстановления используйте проверенную резервную копию. |
| Ошибка записи или системной синхронизации | Сохраните файлы и диагностическое сообщение. Проверьте доступное место и состояние носителя перед повторным открытием копии. Если ошибка произошла во время commit, проверьте состояние соответствующей записи после восстановления перед повтором операции. |

Проверяйте совместимость новой версии на отдельной копии базы. Для возврата к предыдущей версии используйте пару, сохранённую до первого открытия новой версией.

## Защита локальных файлов и ресурсные границы

## Поддерживаемый профиль

Движок предназначен для локального каталога, которым управляет доверенный владелец. Проверки путей отвергают символические ссылки, hard links к файлам и Windows reparse points, включая родительские компоненты. База, WAL, lock, baseline и manifest должны быть обычными файлами. Windows device names, альтернативные потоки `:stream`, UNC/device namespace и неоднозначные имена с завершающим пробелом или точкой отклоняются.

WAL создаётся эксклюзивно, без перезаписи существующего файла. На POSIX новые база, WAL, manifest и lock создаются с режимом `0600`. Каталоги публикации имеют режим `0700`. На Windows права наследуются от родительского каталога: владелец обязан настроить его ACL. Существующий `.rewrite.tmp` не удаляется автоматически: legacy-compaction возвращает отказ, сохраняя и WAL, и посторонний файл.

Проверки являются preflight, а не полной защитой от TOCTOU. `std::fstream` и копирование повторно открывают имена файлов. Поэтому одновременный злоумышленник с правом переименования родительских каталогов или замены файлов остаётся за пределами гарантии. Флаги `O_NOFOLLOW` / `FILE_FLAG_OPEN_REPARSE_POINT` применяются к созданию файлов, lock и durable flush; они не заменяют права на каталог. Общий storage-backend на удерживаемых дескрипторах и directory-relative I/O остаётся отдельной задачей.

## Пределы текущей сборки

| Ресурс | Предел |
|---|---|
| Физические страницы базы / baseline | 131 072 страницы по 8192 байта — 1 GiB плюс файловый заголовок |
| WAL | 256 MiB, включая преамбулу и заголовки кадров |
| Число кадров при replay / append | 100 000 |
| Файл manifest при проверке комплекта | Не более 4096 байт; парсер дополнительно требует точный размер своего формата |

Предел размера WAL проверяется до разбора кадров; предел числа записей — до выделения следующего payload; размер кадра проверяется до выделения его payload. Append проверяет вместимость до записи. Превышение выдаёт `std::length_error`, не удаляет историю и не усекает хвост журнала. LogManager после неуспешного append блокирует дальнейшую запись, как и после других ошибок append; незавершённая операция разрешается обычным recovery при следующем открытии.

Низкоуровневый `WriteAheadLog(path, WalLimits{maxBytes, maxRecords})` позволяет задать явные пределы для специализированных инструментов и тестов. Runtime/CLI используют значения по умолчанию. Это новые ограничения приёма, а не изменение дискового формата: ранее допустимый большой комплект может быть отклонён. Не удаляйте WAL и не редактируйте manifest для обхода отказа. Сохраните полный комплект; увеличение профиля требует отдельной сборки/инструмента и проверки восстановления.

До достижения лимита требуется мониторинг роста. `reduce-wal DATABASE NEW_DIRECTORY` создаёт отдельный проверяемый кандидат v3; автоматической ротации, сокращения на месте и удаления исходного комплекта нет. При превышении лимита источник отклоняется до сокращения: команда не является обходом ограничений парсера. Лимиты входа ограничивают объём работы, но не являются строгим пределом RSS или wall-clock timeout: recovery создаёт дополнительные контейнеры и копии записей.

Кандидат требует хранения `.zdb`, `.wal`, `.zdb.baseline` и `.zdb.snapshot` вместе. После проверки нового пути переключение приложения остаётся явной операцией владельца. Ошибка после публикации может оставить полный каталог: сначала выполните `verify-snapshot`, затем `check`. Оставшийся после process crash каталог `.snapshot-*` не является выбранной рабочей базой и автоматически не активируется. Не удаляйте исходные файлы для освобождения места до независимого резервирования и проверки нового комплекта. Windows использует FlushFileBuffers для файлов и MoveFileExW с WRITE_THROUGH для публикации; отдельного fsync каталога на Windows здесь нет. OS crash и отключение питания этим стендом не проверены.

## Конкурентный доступ

Stage 7 закрепляет single writer через OS ownership базы и отдельный `.wal.lock`. Эти sidecar сохраняются после close/crash; их наличие не означает живого владельца. Не удаляйте lock-файлы для обхода отказа. При наличии selector удерживаются logical source и selected target. Новые raw WAL writers не могут обходить занятый FileManager или писать в архивный source с `.install`.

Low-level graph должен передавать WAL явную `files.ownership()`. Перед `files.closeDatabase()` закрыть dependent WAL (`wal.close()`) и уничтожить BufferManager/его guards. Close с живыми зависимостями отклоняется без освобождения владения. BufferPageGuard должен жить короче кэша; нельзя уничтожать Runtime, пока использующие его threads не завершены. Два независимых cache одного owner запрещены. Windows DOS 8.3 **имена файлов** не поддерживаются, чтобы не разделить lock-domain. [State model, тесты и ограничения Stage 7](STATUS_STAGE_7_DATABASE_LIFECYCLE_WRITER_SAFETY_RU.md).

Stage 6 добавляет явный `install-wal SOURCE.zdb CANDIDATE.zdb`. После committed selector исходный путь — логическое имя, данные изменяются в выбранном reduced-каталоге. FileManager удерживает source и target lock до закрытия, включая низкоуровневый open. Не переносите target и не удаляйте `.install`: это может лишить доступа к подтверждённым после установки данным. Архив source сохраняется и при open проверяется на identity, размеры и наличие sidecar; повреждённый selector/target приводит к отказу без fallback. Временные `.install.pending-*` не выбираются и не исполняются. Полный порядок установки, повторов и диагностики описан в [отчёте Stage 6](STATUS_STAGE_6_CRASH_SAFE_WAL_INSTALLATION_RU.md). Автоматического удаления архивов и поддержки старых writers после установки нет.

Операции RecordManager, проверка согласованности, checkpoint, backup и чтение списка/наличия таблиц используют общий runtime mutex. Это сериализация отдельных операций одного runtime, а не многокомандные пользовательские транзакции или MVCC. Второе открытие той же базы отклоняется межпроцессным lock. Runtime нельзя уничтожать, пока использующие его потоки не завершены.

Набор `ZenthrilDBHardening` проверяет сохранность файлов при отказе на ссылках и лимитах, legacy rewrite, параллельные записи/чтение/проверку и повторное открытие. На Linux отдельно проверяется отказ FIFO без блокировки. Если Windows запрещает создание тестовых symlink, тест явно печатает `SKIP`; hard-link сценарии при этом остаются обязательными. Этот набор не является race-detector или доказательством полной транзакционной изоляции.
