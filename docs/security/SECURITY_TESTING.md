# Проверки безопасности Fortress-20

Stage 0 отделяет доступные проверки локального хранилища от проверок будущих компонентов. Используйте отдельные временные каталоги, синтетические базы и отдельные резервные копии. Проверки с имитацией ошибок ввода-вывода используют специальную сборку с включённым fault injection. Результат считается подтверждённым для зафиксированных платформы, конфигурации, ревизии и проверяемого сценария.

## Локальные проверки

Запустите категорию `security` после сборки с тестами. Укажите фактический путь к каталогу сборки и конфигурацию.

```sh
ctest --test-dir build-ci -C Debug -L security --output-on-failure --no-tests=error
ctest --test-dir build-ci -C Release -L security --output-on-failure --no-tests=error
ctest --test-dir build-ci -C Release --output-on-failure --no-tests=error
```

`ZenthrilDBSecurity` запускает регрессии идентичности WAL, формата заголовка и поколения снимка. В Debug он также прерывает дочерний процесс перед публикацией каталога. Остальные проверки хранилища входят в полный набор. Проверка установленного CLI выполняется отдельным шагом CI.

| Свойство | Тест или сценарий | Проверяемый результат и границы |
| --- | --- | --- |
| Контроль случайного повреждения страницы | `test_page_format.cpp`, `test_crash_recovery.cpp` | Повреждённые данные, Page LSN или заголовок отвергаются в предусмотренных сценариях. CRC обнаруживает ошибки формата и случайное повреждение |
| Отсутствие и повреждение WAL | `test_wal.cpp`, `test_crash_recovery.cpp` | Некорректный CRC приводит к отказу, неполный хвост обрабатывается по спецификации, отсутствующий WAL препятствует открытию |
| Несовпадение UUID базы и журнала | `test_database_wal_identity.cpp` | Чужой WAL с образами заголовка отклоняется до replay и исправления хвоста. Тест сравнивает байты базы и журнала после отказа. Подходящий WAL с неполным хвостом восстанавливается с сохранением подтверждённой записи |
| Привязка WAL без образов заголовка | `test_snapshot_generation.cpp` | Проверяется новая пара с системными, транзакционными и информационными metadata-кадрами. Чужой WAL, прежнее поколение, недостающая граница и повреждённые структуры отклоняются с побайтовой проверкой |
| Прерывание публикации поколения | `test_snapshot_crash.cpp` | В Debug дочерний процесс завершается, когда оба файла подготовлены и конечный каталог ещё не опубликован. Исходная пара сохраняется, повтор операции даёт читаемую копию |
| Физический ремонт страницы | `test_physical_page_recovery.cpp`, `test_physical_recovery_crash.cpp` | Восстановление связанных пар по итоговым образам, повторное открытие, побайтовый отказ при отсутствии образа и аварийный выход после синхронизации ремонта в Debug. [Границы восстановления](../PHYSICAL_RECOVERY_RU.md) |
| Версия заголовка базы | `test_database_wal_identity.cpp` | Заголовок с неподдерживаемой версией отклоняется при открытии, даже когда его CRC верен |
| Взаимоисключающее открытие | `test_file_manager.cpp` | Второй экземпляр FileManager отклоняет открытие при удержании блокировки и открывает файл после её освобождения |
| Ошибка записи и синхронизации | `test_storage_faults.cpp`, `test_wal.cpp`, `test_database_runtime.cpp` | Ошибка передаётся вызывающему коду, выбранные неполные мутации проверяются после повторного открытия. Точки имитации ошибок выполняются в конфигурации с fault injection |
| Аварийное завершение и повторное восстановление | `test_crash_recovery.cpp`, `test_header_recovery.cpp` | Прерывание дочернего процесса и повторное открытие подтверждают выбранные случаи REDO и UNDO. Сценарии роста каталога и точечной имитации записи зависят от конфигурации |
| Проверка восстановленных данных | `test_database_runtime.cpp`, `.github/workflows/ci.yml` | Отдельная копия сохраняет прикладные значения. CI сверяет SHA-256 `.zdb` и `.wal` до открытия, запускает проверку базы и сверяет исходную пару после записи в восстановленную копию |

Привязка для старых WAL опирается на образы заголовка. CRC, UUID и поколение обнаруживают несовместимые пары в пределах [заявленной модели](../WAL_IDENTITY_RU.md). Подпись пары и доверенная защита от отката относятся к отдельным этапам.

## Сценарии для следующих этапов

Номера соответствуют [общей дорожной карте](../roadmap/FORTRESS_ROADMAP.md).

| Проверка | Этап | Условие приёмки |
| --- | --- | --- |
| Полномочия и доступ | 8, 11 | Неразрешённый субъект получает отказ до изменения данных. Смена роли действует на новые операции, а действие фиксируется в аудите |
| Утверждённая конфигурация | 8 | Повреждённая, неподписанная или неподдерживаемая конфигурация отклоняется. Безопасное предыдущее состояние и причины отказа доступны оператору |
| Ключи и ротация | 9 | Копия восстанавливается с разрешённым поколением ключа. Потерянный, отозванный или неверный ключ даёт контролируемый отказ. Прерывание ротации сохраняет доступ к подтверждённым данным по документированной схеме |
| Шифрование и nonce | 9 | Тестовые векторы выбранной библиотеки проходят. Изменённые данные или контекст отклоняются до выдачи открытого текста. Сценарии повторов, аварии и конкурентной записи подтверждают правило уникальности nonce |
| Привязка файлов и защищённая резервная копия | 1, 7, 9 | Подменённые или несовместимые компоненты отвергаются до изменения базы. Подтверждается восстановление из подписанного манифеста и независимое чтение данных |
| Аутентификация и ограничение попыток входа | 11 | Повторные неуспешные попытки в синтетическом окружении активируют только предусмотренный лимит. Доверенный оператор и разрешённые сессии сохраняют предусмотренный доступ |
| Повтор запроса | 10, 11 | Повтор уже учтённого запроса или команды с тем же идентификатором не меняет данные или защитное состояние второй раз |
| Граница SQL | После появления SQL | Тестовые значения остаются параметрами, разбор запроса и проверка полномочий происходят независимо от содержимого этих значений |
| Подлинность события и изоляция агента | 10 | Недействительная подпись, другой тип сообщения, чужая среда, отозванный ключ, повтор после перезапуска и попытка записи за пределами полномочий отклоняются |
| Пропускная способность и отказ агента | 10 | Переполнение очереди, превышение частоты и исчезновение агента видны в диагностике. Новые автоматические действия ограничиваются без ослабления базовой авторизации |
| Воспроизводимость политики | 10 | Фиксированные политика, входы и счётчики дают одинаковые решение и объяснение. Один источник не применяет ограничение самостоятельно |
| Подтверждение, истечение и отмена | 10 | Действие вне каталога автоматически не применяется. Рискованное действие требует подтверждения. Повтор не продлевает TTL, отмена действует только в заданной области, а просроченное ограничение завершается после перезапуска |
| Происхождение поставки | 12 | Пакет сверяется с утверждённым идентификатором выпуска, подписанными метаданными и списком зависимостей. Ошибка проверки блокирует приём пакета |

Для каждой проверки храните ссылку на сценарий, ожидаемый отказ или успешный результат и фактический вывод тестов. Успешный прогон подтверждает заявленные сценарии. Статус `SECURITY REVIEWED` присваивается по результату отдельной независимой проверки с зафиксированным охватом.
