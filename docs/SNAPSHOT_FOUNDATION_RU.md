# ZenthrilDB Stage 5. Базовый снимок и публикация

## Состав снимка

Команда `zenthrildb snapshot data.zdb NEW_DIRECTORY` публикует новый каталог с четырьмя основными файлами.

| Файл | Назначение |
| --- | --- |
| `data.zdb` | Рабочий файл базы. После публикации может изменяться. |
| `data.wal` | Журнал нового поколения. Все полные кадры исходного WAL сохраняют исходные байты и LSN. |
| `data.zdb.baseline` | Полный физический образ подтверждённого состояния на границе снимка. Runtime открывает его для чтения. |
| `data.zdb.snapshot` | Манифест, привязывающий базовый образ и исторический префикс WAL к UUID, поколению и LSN. |

Штатный `data.zdb.lock` защищает открытие рабочего комплекта. Он создаётся по мере необходимости и не входит в контрольные суммы снимка.

Базовый образ содержит файловый заголовок и каждый физический слот, включая страницу 0 с идентичностью, корни метаданных и каталога, продолжения каталога, free-list, свободные слоты и все занятые страницы. UUID базы сохраняется. Генерация создаётся заново, даже если снимок строится из ранее опубликованного комплекта. Runtime проверяет значение поколения в заголовке WAL и на странице 0 обоих файлов данных. Форматы `.zdb` и кадров WAL остались прежними.

## Граница и манифест

На копии выполняется штатное восстановление. Подтверждённые мутации применяются, а незавершённые откатываются согласно проверенному журналу. Snapshot LSN равен LSN последнего полного проверенного кадра, либо нулю при его отсутствии. Верхняя граница Transaction ID включает транзакции с BEGIN до этого LSN независимо от их исхода. Она исключает повторное использование идентификаторов, даже если часть транзакций пришлось откатить. Открытый runtime исходной базы исключает получение исходной блокировки.

Манифест v1 занимает 116 байт. Целые поля записываются в little endian.

| Смещение | Размер в байтах | Поле |
| --- | ---: | --- |
| 0 | 4 | Magic `ZDBS` |
| 4 | 4 | Версия |
| 8 | 4 | Размер манифеста |
| 12 | 60 | WalIdentity с UUID, поколением, границей, размером страницы и собственным CRC |
| 72 | 8 | Максимальный Transaction ID |
| 80 | 8 | Число физических страниц |
| 88 | 8 | Размер базового образа |
| 96 | 8 | Длина префикса WAL, включая преамбулу и кадр на границе |
| 104 | 4 | CRC32 базового образа |
| 108 | 4 | CRC32 префикса WAL |
| 112 | 4 | CRC32 предыдущих 112 байт манифеста |

Чтение проверяет точный размер манифеста, версию, размеры и границы полей. В полном комплекте дополнительно проверяются структура WAL, длина и контрольная сумма его префикса, наличие кадра на границе и верхний Transaction ID. Любой BEGIN за границей должен иметь ID выше этой отметки. CRC32 обнаруживает повреждения в заявленной модели отказов. Аутентификация, подпись и защита от согласованного отката требуют внешнего доверенного состояния.

## Независимая проверка и восстановление

```sh
zenthrildb verify-baseline NEW_DIRECTORY/data.zdb
zenthrildb verify-snapshot NEW_DIRECTORY/data.zdb
zenthrildb check NEW_DIRECTORY/data.zdb
```

`verify-baseline` читает только манифест и базовый образ. Путь `data.zdb` задаёт общий префикс для поиска файлов. Из образа независимо считываются файловый заголовок, идентичность, каждый слот, PageHeader и CRC, типы системных страниц и Page LSN. Валидатор сверяет границы каталога, корни и владельцев таблиц, цепочки записей и продолжений каталога, отсутствие дублей и пересечений во free-list. Размер физического файла должен точно соответствовать числу страниц.

`verify-snapshot` дополнительно проверяет рабочую пару и соответствие её текущих байтов проекции из базового образа и WAL за границей. Команда также проверяет структуру рабочего каталога, free-list и записей после применения этой истории. Обе команды проверки сохраняют байты входных файлов. При полной проверке штатная межпроцессная блокировка может создать `.lock`. Неполный хвост WAL или необходимость записать хотя бы одну ремонтную страницу приводят к отказу проверки. `check` открывает runtime с обычным восстановлением и может исправить рабочие файлы.

При штатном открытии `RecoveryCoordinator` проверяет исходную идентичность и манифест до ремонта. Для физических REDO и UNDO используются только кадры строго после границы. План начинается с заголовка и страниц базового образа. Для первого изменения каждого старого слота before-image должен совпадать с базовым состоянием. Последующие изменения сопоставляются с результатом предшествующих подтверждённых мутаций или отката. Слоты, которые не изменялись после границы, восстанавливаются из базового образа. Для роста файла нужны подтверждённые образы заголовка и новых страниц в суффиксе WAL. Отказ до применения плана сохраняет исходные байты. При прерывании самого ремонта повторное открытие строит тот же план.

Полный WAL сохраняется и считывается для проверки идентичности, последовательности, границы и целостности префикса. Старые page images исключены из физического плана. Отдельная синтетическая фикстура создаёт журнал без этих образов, восстанавливает все слоты после страницы 0, затем проверяет запись после границы и восстановление при неполном хвосте. Это испытание базового алгоритма. Рабочий комплект по-прежнему обязан иметь собственный WAL, совпадающий с манифестом.

Для совместимости пара без обоих дополнительных файлов открывается по прежнему полному пути WAL. Если сохранился только один дополнительный файл, комплект отклоняется. Команда `create` также отклоняет коллизию с любым из этих файлов. Файловый формат этой версии не содержит обязательного маркера наличия манифеста. При эксплуатации сохраняйте все четыре файла вместе.

## Публикация и порядок синхронизации

1. Получить эксклюзивную блокировку исходной базы и создать отдельный каталог рядом с назначением. При наличии назначения вернуть ошибку.
2. Перенести исходные файлы в рабочий каталог. Выполнить recovery копии, зафиксировать границу и записать идентичность нового поколения в преамбулу и страницу 0. Сохранить полный базовый образ из восстановленных данных.
3. Синхронизировать WAL, затем рабочую базу и базовый образ. Записать и синхронизировать манифест. Независимо перечитать файлы и проверить полный комплект.
4. На Linux синхронизировать рабочий каталог, выполнить `renameat2(..., RENAME_NOREPLACE)` в том же родительском каталоге и синхронизировать родителя. На Windows файлы синхронизируются через `FlushFileBuffers`, а перенос каталога использует `MoveFileExW(..., MOVEFILE_WRITE_THROUGH)` без разрешения замены или копирования между томами.
5. Освободить исходную блокировку и вернуть успех после указанных системных операций. До переименования каталог назначения отсутствует. После переименования он содержит уже проверенный комплект. Ошибка на поздней границе возвращается вызывающему, даже если проверенный каталог уже виден. В таком случае проверьте его явно командой `verify-snapshot`.

На Linux `fsync` файла и запись в каталоге имеют разные границы. Публикация требует поддержки `RENAME_NOREPLACE` файловой системой и возвращает ошибку при отсутствии такой поддержки. На Windows отдельного эквивалента POSIX `fsync` родительского каталога в реализации нет. Microsoft отдельно описывает действие `MOVEFILE_WRITE_THROUGH` для переноса как копирования с удалением. Проверки здесь охватывают фактический вызов и видимость каталога на Windows. [Linux fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html), [Linux rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html), [Microsoft FlushFileBuffers](https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers), [Microsoft MoveFileExW](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-movefileexw).

Записи в исходные файлы при создании снимка отсутствуют. Если процесс прерван до публикации, временный каталог остаётся под отдельным именем и автоматически не выбирается. При ошибке операции удаляются только известные файлы из собственного рабочего каталога. Повторная публикация выбирает новое имя рабочего каталога, а существующее назначение защищено от замены. Резервное копирование `backup` сохраняет идентичность и весь комплект Stage 5.

## Испытания и ограничения

Набор `ZenthrilDBSnapshot` проверяет структуру формата, независимое восстановление, физические REDO/UNDO, повторное открытие, свободные страницы и их повторное выделение, дочерние снимки, повреждения, исходные байты и историю WAL. Дочерние процессы аварийно завершаются до копирования, при частичных записях, на границах синхронизации, проверки, переименования и возврата. Ошибки открытия, чтения, записи, закрытия, синхронизации, переименования и ENOSPC имитируются на отдельных временных БД.

Блокировка действует для процессов, использующих тот же sidecar в доверенном локальном каталоге. Копирование между томами, внешние процессы записи, сетевая файловая система, отказы носителя и аппаратное отключение питания находятся за пределами испытаний. Открытие читает полный WAL, поэтому пределы по времени, памяти и размеру журнала остаются задачей измерений. Подтверждённые полные кадры сохраняются. Штатное восстановление рабочей копии может удалить только распознанный неполный хвост. Проект сокращения истории выделен в [Stage 6](roadmap/STORAGE_RECOVERY_NEXT_RU.md).
