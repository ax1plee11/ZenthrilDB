# Критерии релиза ZenthrilDB

Этот список определяет самостоятельный локальный MVP v1.0 по текущей дорожной карте. До прохождения всех обязательных критериев релиз и подключение к Zenthril закрыты.

## Обязательные критерии

| Область | Критерий | Состояние |
|---|---|---|
| Storage reliability | WAL-before-data, durable commit, startup recovery, redo/undo и повторное recovery | Связанные пары проверяют UUID, поколение и LSN. Физическое восстановление доступно при однозначном образе. Safe checkpoint фиксирует границу, сохраняя полный WAL. Открыты сокращение WAL, ремонт заголовка и страницы идентичности, испытания носителя. [Физическое восстановление](PHYSICAL_RECOVERY_RU.md), [Safe checkpoint](SAFE_CHECKPOINT_RU.md) |
| Storage consistency | Атомарность page lifecycle, каталога и free-list; runtime проверяет базу при открытии | Основа реализована; нужен стресс и негативный набор |
| Record layer | Версионированные записи, insert/read/update/delete, ограничения размера и overflow | Реализованы CRUD, атомарные вставка и удаление, многостраничный каталог страниц с чтением старого формата. Одна запись занимает одну страницу. Многостраничные значения, масштабирование каталога таблиц и free-list остаются открытыми. |
| Index | B+Tree с split/merge, повторным открытием и восстановлением | Не реализовано |
| Transactions | Commit/rollback для операций записей и индексов, видимость конкурентных операций | Не реализовано; текущие транзакции не обеспечивают полную изоляцию |
| Query/API | Стабильный пользовательский API; базовый SQL DDL/DML либо утверждённый KV API | Доступен предварительный CLI для KV. SQL и стабильный контракт API остаются открытыми. |
| Concurrency | Интеграция LockManager, дедлоки, отмена/таймауты, конкурентная запись и чтение | Foundation существует; end-to-end не реализовано |
| Portability | Windows и Ubuntu Debug/Release, CI, чистая сборка и тесты | Локальные прогоны проходят на обеих ОС. В GitHub Actions добавлены четыре конфигурации и проверка установленного CLI с восстановлением копии. Удалённый прогон пока не подтверждён. |
| Operations | Формат/совместимость, backup/restore, диагностика повреждений, install/package и upgrade story | Реализованы установка CLI, упаковка и копирование согласованной пары базы и WAL. Процедура восстановления описана в руководстве. Открыты совместимость версий и безопасное ограничение роста WAL. |
| Security | Минимальный профиль безопасности v1.0 | Модель угроз и первый регрессионный тест WAL. Остальные требования ниже. |
| Performance | Нагрузочные тесты, latency/throughput baseline, пределы размера и рост WAL | Не реализовано |
| Release docs | API guide, migration/backup, known limitations, release notes | Частично |

## Stage 4. Safe checkpoint

Runtime подтверждает checkpoint после проверки итоговых образов, синхронизации WAL, файла базы и нового кадра границы. Процедура открытия проверяет UUID, поколение, LSN и верхнюю границу Transaction ID. Сохранённые полные образы остаются доступными для физического восстановления. Критерий сокращения WAL остаётся отдельным. [Спецификация и приёмка](SAFE_CHECKPOINT_RU.md)

## Stage 5. Snapshot Foundation

Тесты проверяют полный базовый образ, манифест, применение REDO и UNDO после границы, восстановление без исторических образов страниц в синтетической копии, публикацию без замены каталога, отказоустойчивость и сохранность исходных файлов. Runtime читает полную историю WAL для валидации. Базовый образ и публикация прошли CTest в Windows x64 и Ubuntu 24.04, Debug и Release. Границы проверки включают аварийное завершение процесса и имитацию I/O, аппаратная долговечность требует отдельного испытания. [Спецификация](SNAPSHOT_FOUNDATION_RU.md), [аудит](SNAPSHOT_AUDIT_RU.md).

## Обязательный профиль безопасности v1.0

| Критерий | Свидетельство для допуска |
|---|---|
| Безопасные файловые операции и защита конфигурации | Закрытые права, проверенные пути и типы файлов, проверка ссылок, атомарные изменения конфигурации, отказ при небезопасных условиях. |
| Целостность заголовков и страниц, защита WAL от подмены | Проверка форматов, CRC, UUID, поколения и LSN до записи в связанных парах. Криптографическая аутентификация содержимого и защита от отката согласованной пары остаются обязательными критериями. |
| Безопасная обработка ошибок и отсутствие секретов в логах | Определённые ошибки, предсказуемое состояние после I/O, тест на отсутствие ключей, значений и секретов в диагностике. |
| Проверка ввода и ограничение ресурсов | Лимиты длины, количества, памяти, времени и роста WAL. Негативные сценарии и измерение использования ресурсов. |
| Безопасное управление ключами | Явное владение, отдельный ключевой провайдер, политики хранения, ротации и восстановления, отсутствие экспорта открытых ключей через API. Тесты ротации, потери ключа и отказа провайдера для задействованных ключевых операций. |
| Негативные тесты и fuzzing критических парсеров | Заголовки, страницы, каталог, WAL и вход Query/API. Воспроизводимый запуск, корпус граничных входов, отчёт о покрытии и устранении найденных ошибок. |

Этапы расширенного шифрования, Sentinel и серверного профиля определены в [архитектуре v1.0 и Fortress‑20](architecture/DATABASE_ARCHITECTURE.md).

## Последовательность реализации

1. Закрепить reliability runtime и страницу/каталог/free-list mutation tests.
2. Реализовать Record Manager и устойчивый heap storage поверх DatabaseRuntime.
3. Добавить B+Tree и atomic coordination между records/index pages.
4. Завершить транзакционную видимость и интеграцию LockManager.
5. Реализовать ограниченный query/API surface, выбранный для v1.0, и end-to-end tests.
6. Добавить backup/restore, format compatibility checks, fuzz/negative tests, CI и install/package.
7. Пройти clean Windows/Ubuntu matrix, нагрузочные проверки и выпускной review.

Каждый критерий переводится в «пройден» только при наличии реализации и воспроизводимых проверок. Сборка сама по себе релизную готовность не подтверждает.
